# Mock Data Reference

All state lives in mock data files + React context. No backend.

## Data files

```
src/data/
  mock-data.ts          — customers, quotes, contracts, invoices, tasks (core)
  revrec-data.ts        — revenue arrangements, obligations, schedules
  support-data.ts       — support tickets, email summaries
  billing-data.ts       — payments, collection cases, credit notes
  ingest-data.ts        — ingestion samples, extracted contracts, approvals
  gettingStarted.ts     — workbench home milestones
```

## Core record types (from `mock-data.ts`)

### Customer

Required:
- id, name, commercialAccount, billingLegalEntity, merchantEntity, segment, tier
- ARR, TCV, prepaidCreditTotal, prepaidCreditBalance, openAr, nextRenewalDate
- riskBadges: string[]
- AE / CSM / billingOwner

Added fields (from Customer tab work):
- `domain` (e.g. "echocorp.ai")
- `industry` (e.g. "AI Infrastructure")
- `region` (e.g. "North America")
- `crmAccountId` (Salesforce account ID)
- `crmSyncStatus`, `crmLastSyncedAt`
- `paymentMethod` (e.g. "ACH", "Wire", "Card")
- `currency`, `taxRegion`, `poRequired`
- `activeContractCount`, `openQuoteCount`

### Quote

- quoteId, customerId, version, source, status
- amount, arr, discountPct
- approvalStatus / approval: `{ status, currentApprover, triggers, ... }`
- products, commercialTerms
- relatedContractId
- timeline events
- crmSyncStatus, crmSyncedAmount

### Contract

- contractId, customerId, sourceQuoteId, status
- signedDate, effectiveDate, term
- minCommit, prepaidCredits (total + balance), overageRate
- billingSchedule (array of scheduled invoices)
- enforcement: `{ status, blockingIssues, productMappingIssues, provisioning }`
- amendments (array)
- invoices (refs)
- revRecSummary
- comparisonToQuote (differences from linked quote)
- `closure?: ContractClosure` — optional early termination data
- `scheduledStartDate?: string` — activation date for Scheduled contracts (= prior contract's closure effectiveDate)
- `replacesContractId?: string` — set on a Scheduled renewal pointing to the prior contract being closed
- `replacedByContractId?: string` — set on a Closing/Closed contract pointing to the new Scheduled renewal

### ContractClosure

- `effectiveDate` — when the contract closes (can be future-dated for wind-down)
- `reason`: `"customer_non_renewal" | "ma_consolidation" | "mutual_agreement" | "non_payment" | "replaced_by_new" | "other"`
- `reasonDetail?` — optional free-text elaboration
- `settlementType`: `"termination_charge" | "credit_note" | "no_financial_impact"`
- `calculatedAmount` — system-suggested amount
- `finalAmount` — operator-confirmed amount (may differ from calculated)
- `invoiceId?` — generated termination invoice ID (when settlementType = termination_charge)
- `creditNoteId?` — generated credit note ID (when settlementType = credit_note)
- `closedBy` — who initiated the closure
- `closedAt` — timestamp
- `approvalRequired` — whether the settlement requires approval
- `approvalReason?` — e.g. "Closure credit note", "Termination-generated invoice"

### Invoice

- id, customerId, contractId, amount, date, dueDate, status
- holdReason, disputeReason (optional)
- Optional enrichments: `billingPeriodStart`, `billingPeriodEnd`, `currency`, `paymentTerms`, `billToContact`, `poNumber`, `taxTotal`, `balanceDue`, `detailedLineItems`, `reviewChecklist`, `deliveryHistory`

### Task

- id, customerId, type, title, assignee, dueDate, status

## Lifecycle-tab data types (from `revrec-data.ts`, `billing-data.ts`)

### InvoiceDetailLine (enriched line item)

- sku, name, type (`recurring` | `one-time` | `usage` | `credit`)
- quantity, unitPrice, discount, tax, netAmount
- `lineType`: `"platform_fee" | "prepaid_credit" | "usage_overage" | "true_up" | "minimum_commit"`

### ReviewCheck

- label, status: `"pass" | "warn" | "fail"`

### DeliveryEvent

- date, method, recipient, status

### CreditNote

- id, invoiceId, customerId, amount, reason, status, date, owner
- `contractId?` — linked contract (for closure-related credit notes)
- `closureRelated?` — boolean flag for credit notes generated by contract closure

### Payment

- id, customerId, invoiceId, amount, method, bankReference, receiptDate
- matchStatus, allocations: `{ invoiceId, amount }[]`, reversals

### CollectionCase

- id, customerId, invoiceId, outstandingAmount, daysOverdue, stage, owner
- ptpDate, nextStep
- followUpHistory: `{ date, action, note }[]`
- escalated, lastContactSummary

### RevenueArrangement

- id, customerId, contractId, status, policy
- obligations: `PerformanceObligation[]`
- schedule: `RecognitionScheduleEntry[]`
- recognizedToDate, deferred
- closeBlockers: `CloseBlocker[]`
- journalExports: `JournalExport[]`
- adjustments, lastRecalculated, closeStatus

### PerformanceObligation

- product, obligationType: `"over-time" | "point-in-time" | "usage-based"`
- allocationBasis, allocatedAmount, recognizedToDate, deferredRemaining, method

### RecognitionScheduleEntry

- period, recognized, deferred, remaining, amended

### CloseBlocker

- description, severity: `"critical" | "warning"`, category, resolved

### JournalExport

- id, period, status, erpReference, exportDate, failReason

## Support & comms types (from `support-data.ts`)

### SupportTicket

- id, customerId, subject
- priority: `"High" | "Medium" | "Low"`
- status: `"Open" | "Escalated" | "Resolved"`
- category (e.g. "Billing dispute", "Invoice question", "Credit burn-down")
- assignee, createdAt, lastUpdatedAt

### EmailSummary

- id, customerId, subject, from, date
- snippet (2–3 sentence summary)
- sentiment: `"positive" | "neutral" | "negative"`

## Ingestion types (from `ingest-data.ts`)

- `SampleDoc` — sample document definitions
- `ExtractedContract` — all fields extracted from a document
- `ExtractedProduct` — per-line product extracted
- `ExtractedTerms` — commercial terms extracted
- `IngestIssue` — blocking or warning issue on extracted contract
- `IngestResult` — created/linked object log after Finish
- `CreatedObject` — one logged object outcome (created / linked / reused)
- `ApprovalRequest` — pending invoice approval record
- `ApprovalComment` — single comment on an approval

## Queue types (from `queue-data.ts`)

- `QueueItem` — one document waiting in the Inbox > Queue
  - `sampleId?` — `"sample1" | "sample2" | "sample3"` (which extracted data set to use)
  - `activeContractId?` — for Early Renewal items: the ID of the active prior contract that must be closed first
- `QueueSource` — `"PDF Upload" | "API" | "CPQ" | "Email"`
- `QueueStatus` — `"Pending Review" | "In Progress" | "Ingested" | "Failed" | "Rejected"`
- `QueueScenario` — `"New Business" | "Renewal" | "Amendment" | "Early Renewal"`
- `queueGroupMeta` — group definitions for the Queue index page

## Approval policy types (from `approval-policy.ts`)

- `ApprovalPolicyMode` — `"auto-approve" | "always-approve" | "non-standard"`
- `NonStandardConditions` — high TCV (with $ threshold), discount above threshold (with % threshold), custom payment terms, backdated invoice, manual line items
- `ApprovalPolicy` — `{ mode, conditions }`
- `InvoiceFieldOverrides` — operator-edited invoice fields on the Approval Detail page (amount, dueDate, paymentTerms, billingPeriod start/end, taxRate, poNumber, memo, invoiceDate)
- `QueueItemOverride` — runtime status / contractId / invoiceId override for a queue item
- `PendingRenewalIngestion` — keyed by prior contractId; set when "Proceed to Close" is clicked on an Early Renewal queue item. Fields: `queueItemId`, `sampleId`, `renewalTcv`, `customerId`, `pendingContractId`. Cleared after closure approval triggers auto-ingest.
- `DEFAULT_POLICY`, `DEFAULT_NON_STANDARD` — initial values used by the modal

## React context

### `src/context/IngestContext.tsx`

- `selectedSample` — which sample was chosen (`sample1` | `sample2` | `sample3` | `null`)
- `sessionCustomers` — customers created during the session
- `sessionProductSkus` — product SKUs created during the session
- `sessionContracts: Contract[]` — runtime contracts created by auto-ingest (e.g. Scheduled renewal after closure approval). Merged into `customerContracts` inside `CustomerRevenueWorkspace`.
- `addSessionContract(contract)` — append a runtime contract (called during Early Renewal auto-ingest)
- `ingestResult` — result of the last completed ingest
- `approvalRequests` — list of all approval requests in session
- `submittedInvoiceIds` — set of invoice IDs submitted for approval
- `invoiceStatusOverrides` — map of invoiceId → overridden status string
- `invoiceFieldOverrides` — map of invoiceId → editable field overrides (amount, due date, payment terms, billing period, tax rate, PO, memo, invoice date)
- `queueItems` — merged seed + runtime overrides (use this, not the raw `queueItems` from `queue-data.ts`, in components)
- `applyQueueItemOverride(id, override)` — flip status / link contract+invoice IDs
- `firstApprovalCompletedFor` — keyed by `ingestId` (queue item ID); true once the first invoice has been approved through that ingest cycle
- `markFirstApprovalCompleted(ingestId)` — set the flag
- `approvalPolicy` — merchant's invoice approval policy captured via `ApprovalSettingsModal`
- `setApprovalPolicy(policy)` — write the policy
- `contractClosures` — map of contractId → `ContractClosure` (runtime closure state)
- `applyContractClosure(contractId, closure)` — apply a closure to a contract
- `creditNoteStatusOverrides` — map of creditNoteId → status string (for closure-generated CNs)
- `setCreditNoteStatusOverride(creditNoteId, status)` — update a credit note status
- `closureToast` — `{ message, contractId } | null` for toast notifications
- `showClosureToast(message, contractId)` / `clearClosureToast()` — toast control
- `pendingRenewalIngestions: Record<string, PendingRenewalIngestion>` — keyed by prior contractId; set when "Proceed to Close" is triggered for an Early Renewal queue item; cleared when closure is approved and the renewal is auto-ingested
- `setPendingRenewalIngestion(contractId, data)` / `clearPendingRenewalIngestion(contractId)` — manage pending state
- `renewalToast` — `{ message, customerId } | null` — blue toast shown when a renewal is auto-scheduled after approval
- `showRenewalToast(message, customerId)` / `clearRenewalToast()` — toast control

Uses `useState` only — no localStorage / sessionStorage. Refresh resets all session state.
